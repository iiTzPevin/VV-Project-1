Register Policy

The register map from dut/axil_regfile.sv, driven one access at a time. The instinct this widget exists to break: "registers are just more signals — write one, read it back, done." A register carries a policy — RO, RW, W1C, locked — and a read-after-write check tests exactly one of them.

After reset, software writes LOCK = 1, then SECURE = 0xDEADBEEF, then reads SECURE back. What does the read return?

What this models. The write path and read mux of dut/axil_regfile.sv, transaction by transaction: CTRL (0x0, RW) and LOCK (0x4, RW) store; STATUS (0x1, RO) ignores writes and reads back its fixed pattern 0x5A5A_0F0F; INTR (0x3, W1C) clears the written 1-bits and keeps the 0-bits; SECURE (0x5, locked-RW) stores only while LOCK.bit0 == 0 — a locked write is dropped and hardware latches INTR[0], the security-violation interrupt. Reads are registered: rdata/rvalid arrive one cycle after the read request. SCRATCH and the unmapped addresses are left out here; the semantics shown are the spec's, unabridged.

The mutant is from the released pool — secure_writable_locked in tb/axil_ral/mutants_released.yaml: the lock guard is deleted, the violation latch is not. So the alarm still rings while the door opens — and a read-after-write check on SECURE, which failed against the working DUT, passes against the broken one. In the Week 10 demo (measured, DEMO_SEED=5), read-after-write straight down the map scores 3/8 and every policy mutant survives it; reset walk + bit-bash + policy walk score 8/8 as one suite.
