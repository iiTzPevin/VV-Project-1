UVM Phases

The instinct says UVM is a huge new framework to learn from scratch. Assemble it and look: the same driver, monitor, and scoreboard you built in Week 4, wearing standardized names. The new machinery is the phase schedule — build top-down, connect bottom-up, then run — and the schedule has two kinds of failure worth meeting on purpose: the loud kind that names your wiring, and one silent kind that hands you a passing test with a checker that never heard a thing.

What this models. The pyuvm schedule from code/demos/wk09-s1-agent: build_phase creates children parent-first (top-down), connect_phase wires ports child-first (bottom-up, after everything exists), port bindings are resolved once at end_of_elaboration, and simulated time passes only in run_phase. The failure modes are the standard ones. Wiring in build reaches for agent.monitor before agent.build_phase has run — a null handle, loud. Creating a component after build violates the schedule contract — loud. A seq_item_port requires one binding at elaboration, so forgetting it is loud. An analysis port requires zero — ap.write broadcasts to whoever subscribed, and zero subscribers is legal — so forgetting that one is silent, and the test passes with the scoreboard starved. A connect() issued during run lands after resolution: a warning, and no binding. Marker messages follow SystemVerilog UVM's checks (ILLCRT, the minimum-connection resolution error); in pyuvm the same wirings die too, with Python's own errors — and the unconnected analysis port stays exactly as silent. Five items per run; payloads come from a seeded PRNG (mulberry32, seed 5) so every run replays exactly.
